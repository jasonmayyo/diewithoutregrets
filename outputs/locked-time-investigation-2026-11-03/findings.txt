Reproduced failure
The October 22 build-67 commit is 4b3f093. Its budget display calculation is identical
to the historical calculation extracted and tested by reproduce.py (76a1b7c^).
1. A 15-minute allowance is exhausted and state becomes locked.
2. On a subsequent day, refresh() treats yesterday's used time as zero even while locked.
3. The display reports 15 minutes remaining, while the lock remains in effect.
4. In the old home UI, study/emergency controls are inside a lock reveal that requires
   the countdown to reach zero. If this grant's reveal has not already played,
   the positive countdown keeps the controls hidden.

Current source already contains the correction
Commit 76a1b7c, October 30, introduced GuardBudgetSnapshot and the manual home unlock
bar. Locked users show zero remaining and have an unlock entry independent of the
displayed allowance. The fix postdates the October 22 public release.

Validation and limits
reproduce.py completed with exit 0. It reproduced the old display mismatch and passed
six current-code check groups, including stale/missing locked budgets, unlock-entry
eligibility, current/stale metering and pending-grant failure/retry/idempotence.
See results.txt. Production state/contract code runs with in-memory preferences;
iOS scheduling adapter blocks are excluded. Actual iOS shield behavior, SwiftUI
animation timing and cross-process races were not simulated. CoreSimulator was not
accessible in the sandbox. No application source was changed in this investigation.

Recommended next action
Ship the existing locked-budget display and always-available locked-state unlock-entry
fix in the next App Store release. Verify a lock carried overnight before release,
including an app that has not displayed that grant's lock reveal. Do not assume a
new grant or reinstall is needed to migrate the retained lock: the current read path
derives zero directly from locked state and exposes the manual unlock action.
Treat a desired daily unlock/reset as a separate product-rule change, since both
current reset paths deliberately preserve locks. Add an app ID/version and diagnostic
context to customer support reporting so future reports can be tied to actual events.
